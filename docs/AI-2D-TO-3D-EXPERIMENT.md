# ElseMesh image-guided 3D warehouse experiment

**Status: PARTIAL — local experiment, not a production release.** Branch: `experiment/ai-2d-to-3d-world`. The source branch for this work was `codex/procedural-world-test` at `4be987e55a1de665210cf71b6770dbf05a472dbf`. The canonical `main` checkout was not edited. No deployment, push, external model run, or purchase occurred.

## Architecture and feasibility

ElseMesh uses its own WebGPU renderer and scene graph, its GLB loader (`src/engine/loaders/GLTF.js`), authored world recipes, box collider records, and GPU timestamp instrumentation (`src/engine/Bench.js`). This is not a Three.js runtime. Building #001's island entrance is a portal into a separate warehouse interior at approximately `(300,18,300)`; the visible island entrance is a sign and ring, not a continuous exterior warehouse shell. Building #002 is a separate existing GLB. The original warehouse interior contains 1,755 authored objects, including the C64. The procedural branch already streams seeded terrain chunks and retains the home island. The candidate therefore lives in a separate opt-in gallery beside Building #001's interior at `(360,18,300)`. The current result does **not** place a continuous warehouse shell on the island.

The source package is `experiments/ai-2d-to-3d/`: two genuine captures of the earlier running ElseMesh browser, an editable building specification, and provenance. The exterior image shows the island portal, not the building shell. The interior image supports brick, factory windows, roof steel, loft, and concrete floor. The 32 × 30 × 12 m calibration comes from `PortalInteriorRecipe.js`, not photogrammetry. Exterior faces, flat roof, north entrance, hidden layout, and loft dimensions are inferred. An image cannot establish unseen geometry. Input hashes are embedded in the asset sidecar. The generated asset is a **Codex-authored parametric interpretation**, not an automated image-to-mesh model.

## Pipeline and runtime

`warehouse.spec.json` -> `tools/ai-2d-to-3d/build-warehouse.mjs` -> standard GLB plus JSON collision/provenance sidecar -> ElseMesh's GLB loader -> native Mesh/BufferGeometry and collider records in `src/world/ImageGuidedWarehouse.js`. The backend boundary is the versioned JSON spec and GLB/sidecar pair, so another offline generator can be evaluated without changing the renderer. The output is reproducible from the checked-in spec and references:

```powershell
node tools/ai-2d-to-3d/build-warehouse.mjs
npm test
npm run build
npm run dev
```

Open `http://127.0.0.1:5173/?procedural&aiWarehouse` (use Vite's announced port if 5173 is taken). `?aiWarehouse` enables the panel; omit it to use the existing path. The panel shows the references and build record and provides candidate/original visit and visibility controls. A candidate exit returns to the original warehouse. The original island portal, authored warehouse objects, computers, roads, vehicles, and saves were not replaced. The candidate currently has no editable in-game geometry or persistent modifications; edit the spec and regenerate the GLB offline.

The generated GLB is 13,064 bytes, 105 named parts, 1,260 triangles, with 47 collider records. It has an open entrance, floor, walls, windows, roof, columns, and loft. Its unit-box mesh data are shared inside the GLB. One local generator invocation took 254 ms wall time including Node startup; this is not a statistical generation benchmark. The GLB hash remained `9a0f331974cf46c6a5d337a6a7f3f879f036064942ad6a7e496382df9c5da286` on regeneration. Browser validation loaded the GLB through the actual renderer; ordinary forward input crossed the entrance, a wall blocked movement, the floor held the player, original/candidate switching worked, and the original C64 returned `4` for `PRINT 2+2`. The candidate is visually plain and its window/door proportions and roof are not proven architectural matches. There is no texture reconstruction or photorealistic fidelity.

## Evidence and benchmark interpretation

Machine-readable results, three inspection screenshots, and the video are retained in `experiments/ai-2d-to-3d/evidence/`. Raw frame captures and rejected takes are in private local directories outside the repository. The final browser test (`browser-check.json`) observed a 68.1 s cold load in local headless Chrome, 105 imported parts, 47 colliders, and the original 1,755 objects. It blocked a vehicle-controlled visit, crossed the doorway to z=291.65 at floor height 18, stopped at the west wall, restored the original interior from free camera, and verified `PRINT 2+2` yielded 4. The earlier baseline at the **island portal**, before this experiment, sampled 20.53 average FPS and 12.02 FPS 1% low with 82.38 s cold load. It used a different camera and must not be interpreted as a before/after improvement. GPU memory was unavailable; JS heap is not GPU memory.

At a fixed 1280 × 720 viewport, balanced profile, render scale 0.75, frozen procedural streaming, and a candidate-facing view, six alternating 3.2 s rAF runs gave callback rates of **45.56–47.66/s off** and **46.28–49.88/s on**. CPU medians were 18.8–20.3 ms off and 21.9–26.6 ms on. The variation and short runs do not establish an FPS gain; these are headless render callbacks, not display refresh measurements. The first benchmark had a 764 × 429 viewport and was rejected; the retained corrected data are `ai2d3d-benchmark-v2.json`.

With the same fixed review view and ElseMesh GPU timestamp queries, two 60-frame off/on pairs measured mean GPU time **40.11 / 39.35 ms off** and **34.44 / 33.71 ms on**. All 240 queries were captured. The primary change was water/transparent work falling from roughly 7.7–7.9 ms to 2.3–2.4 ms because the warehouse occluded ocean pixels. Opaque pass cost increased slightly (roughly 6.9–7.0 to 7.1–7.2 ms). This is **view-specific occlusion**, not proof that adding a building speeds up scenes generally. GPU allocation size, system memory, frame-time 1% lows across multiple devices, and controlled load-time deltas are unqualified.

The continuous 41.6 s, 1280 × 720 video `evidence/elsemesh-2d-to-3d.mp4` contains 184 Chrome CDP `Page.screencastFrame` images from the running ElseMesh browser. It decoded without error. Its `recording.json` labels scripted navigation, frame receipt timestamps, model/stage, and the actual C64 output. Camera positions are scripted for repeatability; movement through the candidate entrance uses normal player input. The recorded player position moved from `(360,18.08,281)` to `(360,18,288.49)` through the doorway. CDP metadata timestamps were incomplete, so monotonic Node receipt times were used for video pacing. The effective video frame rate is about 4.4/s because capture sampled the game, **not** because the game rendered only 4.4 FPS. Screencast frame count is not an FPS benchmark. A rejected first take had an invalid walk route, and two later takes exposed a capture configuration that stalled game frames. A short probe showed that recording every second frame at JPEG quality 70 preserved 125 game callbacks over four seconds compared with 129 without capture. Those failures are retained as evidence, not edited into a success video. A live reload interrupted one additional rejected take. The video predates the final gallery save guard; the final browser test and save/reload test qualify that guard.

## Procedural-world path

Keep AI-assisted generation offline. Store approved GLB, sidecar, provenance, and hash in a content-addressed asset catalog. Seeded world placement should select catalog IDs and deterministic transforms, never call a model in the game loop. Stream buildings with terrain chunks, use simplified distance meshes, instantiate collision only nearby, reserve the home island's protected footprint, and persist player edits as overlays keyed by world seed, chunk, and structure instance. The present gallery prototype does not implement this placement or modification persistence.

The current importer accepts flat named nodes with one triangle primitive each, translation and scale, a shared box mesh, and a separate box-collision sidecar. It does not consume a Blender hierarchy, arbitrary node rotations, or generated collision geometry. Any Argon or other backend would need an export normalizer and independently reviewed collision proxies before it could use this adapter. Candidate loading now checks whether the gallery was disposed while fetching and clears partial materials, meshes, and colliders on load failure; streaming and repeated device-loss recovery remain unqualified.

## Qualification and rollback

**PARTIAL.** Genuine importable, inspectable 3D geometry and basic collision passed in the real ElseMesh browser, and original C64 interaction survived. A completion review found that gallery coordinates could overwrite the procedural save. The code now saves a safe position before entry and excludes gallery coordinates while inside; a save/reload regression test and the final browser check passed. Architectural fidelity, automated reference interpretation, placed exterior on the island, player-edit persistence, Argon parity, mobile/other-GPU qualification, and GPU-memory measurement did not pass or were not attempted. No production claim follows from this experiment.

To disable the experiment at runtime, load the URL without `aiWarehouse`; the module is created only for that flag. To remove it from a development checkout, switch back to the source branch or revert this experiment's local commit. Original scene assets and saved worlds are unchanged. No production deployment was made.

## Architect gate record

- **PLAN gate:** Before implementation, architect challenged single-image geometry inference, disconnected portal topology, weak benchmarks, and fabricated video risk. Decision: immutable reference provenance, editable offline specification, genuine GLB import beside the original, opt-in UI, matched-view benchmarks, and continuous capture.
- **NO-PROGRESS gate:** Two doorway recording failures under the same screencast settings triggered review. Architect requested instrumented capture versus no-capture motion evidence and position-based completion. Probe isolated screencast overhead; capture frequency/quality was lowered and walking completion now checks player position. The rejected takes are retained.
- **COMPLETION gate:** Architect initially held the reviewed snapshot because temporary gallery coordinates could enter the persistent procedural save. It also identified vehicle/freecam navigation bypasses, weak C64/doorway assertions, partial-load cleanup, and limited Blender export compatibility. The primary added the save guard and reload test; guarded vehicle visits; corrected freecam return; tightened C64 and doorway checks; and added partial-load/disposal cleanup. The final browser test passed with no exceptions, 105 imported parts, doorway/wall/floor movement, original C64 result, and zero active candidate colliders after hiding. The importer contract and remaining lifecycle/device coverage limits are disclosed above. Decision: release no production build; deliver the bounded **PARTIAL** local experiment.
